# 多方式联动规则（transit.py 的判断依据）

这一份讲清楚：**为什么要把火车、地铁、公交、天气放在一起看**，以及每条规则背后的坑。

---

## 1. 一次出行 = 若干段（Leg）

统一模型（见 `scripts/transit.py`）：

| 字段 | 含义 |
|------|------|
| `mode` | train / metro / bus / walk |
| `origin` / `dest` | 起点、终点（**尽量用站名，不要用泛化地名**） |
| `depart` / `arrive` | 发车/到达时刻（datetime，可能跨天） |
| `duration_min` | 时长 |
| `cost` / `cost_text` | 费用（火车票接口不给，脚本不估算） |
| `detail` | 方式特有明细（车次/席别、逐站时刻、线路方向…） |
| `warnings` / `notes` | 该段的坑 |

---

## 2. 跨城还是市内：怎么判

按优先级：

1. `--mode` 明确指定了方式 → 照办；
2. 起点和终点各自解析出**不同的地铁城市** → 跨城；
3. 两端都是 **12306 车站名**（能查到电报码）→ 跨城；
4. 起点是火车站、终点是另一座城市的某个地点 → 跨城；
5. 其余 → 市内。

「城市」的判定顺序（`MetroAdapter.city_of`）：

```
城市名精确匹配  ->  城市名前缀匹配（“上海虹桥”-> 上海）  ->  全网车站名索引（“陆家嘴”-> 上海）
```

全网车站索引覆盖 55 城 9000+ 车站，首次构建几秒，页面有磁盘缓存（12 小时）。

---

## 3. 铁路站名 ≠ 地铁站名（最容易接不上的一环）

| 12306 | 地铁 | 城市 |
|--------|------|------|
| 上海 | 上海火车站 | 上海 |
| 上海虹桥 | 虹桥火车站 | 上海 |
| 长沙南 | 长沙火车南站 | 长沙 |
| 北京南 | 北京南站 | 北京 |
| 深圳北 | 深圳北站 | 深圳 |

映射规则（`transit.py: station_core` / `build_rail_metro_xref`）：

1. 去掉「站 / 火车站 / 火车 / 高铁」等词，得到**核心词**；
2. 核心词完全相同 → 直接对应；
3. 铁路核心词以地铁核心词结尾（`上海虹桥` vs `虹桥`）→ 对应；
4. 地铁核心词以铁路核心词结尾 → 对应。

查不到对应时，退回**城市同名站**（如郴州 → 长沙），再退回「目的地地铁站」。

---

## 4. 换乘缓冲

| 换乘 | 建议最小间隔 | 为什么 |
|------|--------------|--------|
| 火车 → 地铁/公交 | 20 分钟 | 出站、验票、找地铁站、进站 |
| 火车 → 步行 | 15 分钟 | 出站 + 步行到目的地 |
| 地铁 → 公交 | 8 分钟 | 出站换乘 |
| 地铁 → 步行 | 5 分钟 | 出站到地面 |
| 地铁站内换乘 | 4~8 分钟 | 跟着指示牌走，巨型枢纽（北京南站）可能要 10 分钟 |

脚本会自动比对每两段之间的时间差，**不够就报警告**。

## 5. 首末班车：跨方式最容易翻车的地方

### 地铁

`metro_query.py station <城市> <车站>` 给的是**每条线 × 每个方向 × 每种日期类型**的首末班：

```
工作日(周一至周四) / 周五 / 周六 / 周日、国定假日
```

跨日末班用 `data-service-day-offset="1"` 标记（例：周五末班 `00:18` = **次日** 00:18）。
脚本把末班折算成「从当天零点起的分钟数」（可 >1440），所以「当天最晚一班」算出来是**次日 00:36** 而不是 00:36。

**场景**：坐 23:40 的夜车到上海，落地 05:30 —— 地铁首班 05:30 才有，等于要等 30 分钟；
如果落地 04:00，地铁还没开始运营，只能打车。

### 公交

`bus_query.py route` / `lines` 会给**首班/末班**；实时车辆接口在末班后不再更新，
这时要照实说「末班已开走」并给出首班时间。

### 火车

12306 接口不给「落地后当地地铁还有没有车」这种信息 —— **只有把两边的数据放一起才知道**，
这就是 `transit.py` 存在的理由。

## 6. arrive-by 反推

「我 18:00 必须到天安门」不是「查 18:00 的车」，而是**倒推**：

```
arrive_by = 18:00
  -> 市内段必须在 arrive_by 之前结束（预留步行/进站时间）
  -> 反推最晚能坐的火车
  -> 12306 里挑「能赶上、且尽量晚出发」的那班（少候车）
```

若当天所有车次都赶不上，脚本挑**最早到达**的一班并明确警告：
「当天没有 18:00 前到达的车次；最早的一班 21:47 到，请考虑前一晚出发或改其它交通方式」。

同理 `--depart-at` 会排除「发车太早、不符合要求」的车次。

## 7. 天气怎么影响出行

`transit.py journey --weather` 会拉目的地城市天气，规则：

| 天气情况 | 建议 |
|----------|------|
| 有橙色/红色预警（暴雨、台风、暴雪） | 改期，或换成地铁/高铁（地面公交与步行最先受影响） |
| 中到大雨 | 优先地铁，步行段加 10 分钟 |
| 雨夹雪/大雪 | 地面公交易延误，预留余量 |
| 高温/低温预警 | 减少户外停留，景点调整到早晚 |

脚本只**陈述事实**（天气 + 预警），**决策建议由模型给**。

---

## 8. 为什么地铁优先、公交兜底

| 维度 | 地铁 | 公交 |
|------|------|------|
| 准点性 | 高 | 受路况影响 |
| 票价 | 明确（交通卡/现金两档） | 一般 2 元 |
| 首末班 | 有逐方向逐日期的时刻表 | 有但粒度粗 |
| 覆盖 | 55 城，覆盖城市主干 | 覆盖到乡镇 |
| 实时性 | 无实时车况 | **有实时车辆位置** |

所以：**能用地铁就用地铁**；地铁到不了的地方、或者用户要「还有几分钟到」，再用公交。

---

## 9. 车内段衔接的锚点

编排时每一段的终点就是下一段的起点，锚点优先级：

1. 铁路站名 → 地铁站（映射表）
2. 地铁站名 → 直接用
3. 地标 → 留在最后一段做步行提示

**不要**用「人民广场附近」这种泛化地名当锚点 —— 会匹配到错误的站。
